# Photo-Sync-For-MSR1

面向铭凡 MINISFORUM MS-R1（此芯 P1 / ARM64）的私人照片管理与加密云备份项目。

> 当前版本：**0.10.0 分离账户与强制 2FA 原型**。已实现最大 10 GiB 分片续传、精确去重、照片/视频预览、显式 Live Photo 配对、持久化日志及 SnapRAID 只读监控 / 告警；人脸识别、NPU、加密归档和 115 同步尚未实现。下方需求描述是完整目标，不代表所有功能已完成。

详见 [大视频、Live Photo 与 MS-R1 验证说明](docs/MEDIA.md)。FFmpeg 为可选依赖，软件转码尚未在 MS-R1 实机验证。

[日志与 SnapRAID 只读监控说明](docs/LOGGING.md)：日志已实现；SnapRAID sync / scrub / fix 尚未接入，命令成功不会被当作完整健康验证。

[首次初始化与目录索引](docs/INITIALIZATION.md)：原地导入、定期重扫、路径重绑与升级备份，不要求搬到新目录。

[独立初始化与登录流程](docs/SETUP.md)：创建管理员 → 批量目录 → SnapRAID 接入或跳过 → 确认 → 登录；登录后才能访问照片。

[SnapRAID 磁盘与模式选择](docs/SNAPRAID-DISKS.md)：选择磁盘角色与单/双/三校验，由工具生成配置。当前保存方案，首次同步尚未接入。

[客户端与管理台架构](docs/ARCHITECTURE.md)：`/client` 浏览与上传，`/admin` 服务端管理，`/admin/settings/snapraid` 单独调整 SnapRAID。首次引导不参与日常设置。

[账户、2FA 和同步策略](docs/ACCOUNTS-MFA.md)：初始管理员仅登录服务端，由管理员创建客户端用户；两侧强制验证器认证，客户端本机同步与设备认证独立。

## 快速启动原型

需要 Python 3.9+，先安装锁定依赖：

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m server.app
```

浏览器打开 http://127.0.0.1:8080。使用 Ctrl+C 停止。原片与 SQLite 数据默认保存在 `data/`，重启后保留。

```bash
# 自定义端口与持久化目录
.venv/bin/python -m server.app --port 8081 --data /path/to/photosync-data
# 运行集成测试
.venv/bin/python -B -m unittest discover -s tests -v
```

原型提供分离账户与强制 TOTP 2FA，默认只监听回环地址；远程部署需 HTTPS 反向代理及 --secure-cookies。尚未在 MS-R1 上验证。不应直接向公网开放。文件签名检查不是完整图片解码验证。

- `client/`：浏览器客户端，仅照片浏览、上传与预览。
- `server/admin/web/`：独立服务端管理台、初始化、登录与 SnapRAID 日常设置。
- `server/`：HTTP API、SQLite 元数据、内容寻址原片存储。
- `tests/`：并发去重、重启持久性、原片读取及请求边界测试。
- [API 说明](docs/API.md) · [版本管理规则](docs/VERSIONING.md) · [变更记录](CHANGELOG.md)

当前先制作独立客户端 / 服务端原型用于交互和接口验证，最终是否复用现有相册仍可在后续评估。

## 1. 项目目标

对标 Immich / PhotoPrism 的照片上传、浏览及人物相册体验，重点实现：

1. 上传照片并按人物自动归类，不做视觉问答。
2. 基于原始文件 SHA256 去重，重复上传不产生多余的原片副本。
3. 自动将新增照片分批打包、加密，并同步到 115 网盘。
4. 评估此芯 P1 内置 NPU 对人脸检测与特征提取的加速能力。
5. 集成 SnapRAID 管理，通过异步任务为照片与视频提供本地多盘校验保护。
6. 面向 MS-R1 的 Debian / ARM64 环境部署，并评估 PVE 下的可维护部署方式。

## 2. 已确认的需求方向

### 2.1 照片管理与人物相册

- 提供照片上传工具，以 Immich / PhotoPrism 为产品参考。
- 检测照片中的人脸，提取人脸特征，对同一人物的照片进行归类。
- 人像识别用于照片整理，不需要聊天、图片问答或生成式视觉语言模型。
- 产品基线拟包含：照片列表、时间线、原图查看、处理状态和人物相册；具体首版范围待确认。
- 拟提供人物命名、合并、拆分和误识别纠正，避免自动分类错误无法修复。

### 2.2 SHA256 精确去重

- 服务端根据上传的原始文件内容计算 SHA256，不信任客户端提供的哈希作为最终依据。
- 同一存储范围内，相同 SHA256 的文件只保存一份原片；再次上传返回已有资源或关联到已有文件。
- 同时上传相同文件也不能产生重复原片；需要数据库唯一约束及文件落盘的幂等处理。
- 重复上传不重复生成缩略图、执行人脸分析或进入新的云端归档包。
- 哈希针对完整原始文件；修改 EXIF、重新压缩或转格式后的文件可能有不同哈希，按不同文件处理。
- 画面相似但字节不同的照片，暂不自动合并或删除。
- 缩略图、人脸裁剪等衍生文件与原片分别管理，不计作重复原片。
- 已实现用户媒体访问关联与底层全局 SHA256 去重；去重不会自动授予其他用户读取权限。

### 2.3 自动加密归档与 115 同步

- 后台自动将新增照片组成增量归档包，分批上传到 115 网盘。
- 采用可配置的时间或容量阈值触发打包；具体阈值待实测确定。
- 使用成熟的加密方案，不自行设计密码算法；最终格式和密钥管理方式待验证确定。
- 云端不应暴露原始文件名、照片元数据或明文归档清单。
- 维护照片 SHA256、归档包、包内路径及远端标识之间的索引；可恢复清单随包加密保存。
- 打包和上传需幂等；任务重试不得将同一照片反复归档。
- 中断后可恢复任务，保留失败原因，支持重试；断点续传取决于所选 115 接口能力。
- 记录打包、加密、上传、校验等阶段的状态，不能仅因请求发出就标记备份成功。
- 支持下载、解密和恢复，恢复后以原片 SHA256 校验内容一致。
- 首版建议保留本地原片；自动清理本地原片需另行确认。
- 115 是加密备份目的地；加密包内的照片不能依赖 115 直接在线浏览。
- 加密密钥需要独立备份，恢复流程不能只依赖原 MS-R1 上的数据库和配置。

### 2.4 SnapRAID 本地多盘保护（只读检查与日志已实现，完整集成待开发）

在工具中集成 SnapRAID 的配置检查、状态查看、异步同步与校验任务，并与 115 加密云备份分别展示结果。

**保护语义**：SnapRAID 通过数据盘、校验盘和 content 元数据提供基于上次同步状态的恢复能力，不会自动把每张照片复制到其他数据盘；新文件在成功同步前尚未纳入该次校验保护。若需要“多个磁盘各有完整照片副本”，还需另外设计复制策略，不能将 SnapRAID sync 当作文件镜像复制。115 备份继续独立保留。

拟议功能与任务流程：

- 查看数据盘、校验盘、挂载状态、可用空间、最近成功同步时间、待保护变更和校验结果。
- 支持手动触发及计划任务；任务在后台执行，提供排队、运行、成功、失败、取消和日志状态，不阻塞上传请求。
- 同步前执行配置与挂载检查及 `diff`；检查盘身份、异常删除 / 修改数量与阈值，避免磁盘未挂载时把缺失数据同步为删除。阈值与异常处理策略需配置并验证。
- `sync`、`scrub` 等阵列操作使用跨进程互斥锁，应用、系统定时任务及 SnapRAID daemon 不得重复调度同一阵列。
- 同步后查询 `status`；定期对已同步阵列执行 `scrub`，展示真实退出状态、校验错误及保护时间点，不将“任务启动”视为“保护完成”。
- 上传分片位于受保护目录之外，文件完成 SHA256 校验并原子发布后再进入保护范围；同步时通过已验证的写入协调或快照机制确保读取状态稳定。
- 人工取消或异常退出后标为待检查，重启后核对实际进程与阵列状态，不直接标记成功或自动发起并行重试。
- `fix` / 恢复属于可能改写文件的单独操作，需要明确目标、差异检查和确认流程，不在普通同步失败后自动执行。
- 维护媒体资源与保护批次的关联；分别显示“本地已保存”“SnapRAID 待同步 / 已保护”“115 待备份 / 已校验”，不能相互替代。

定期健康检查与醒目告警（必需）：

- 定时执行只读健康检查，检查周期、超时时间、最大容许未同步时长和 scrub 过期阈值可配置；默认值在目标磁盘实测后确定。应用启动后也需安排检查，不能只依赖网页打开时检查。
- 检查 SnapRAID 命令是否可执行、配置可读性、实际磁盘挂载及身份、空间阈值、content / parity 文件可访问性、`status` 结果，以及最近成功 sync / scrub 的时间和结果；具体可判定字段需按选定版本验证。
- 区分“健康检查正常”“数据已同步”“完整校验通过”。轻量 status 检查不能替代读取数据的 scrub，也不能证明所有文件没有损坏。
- 状态包括正常、警告、严重异常、未知 / 检查过期、维护中；未配置、检查失败、超时、命令缺失、结果无法解析或长期未检查不得回落为正常。
- 数据盘缺失 / 挂载身份不符、校验错误或阵列不可访问等显示严重异常；待同步、长时间未 sync / scrub、空间不足等按可配置规则告警。保护时间点及尚未保护的数据必须可见。
- 首页和存储 / 备份页显示持续可见的全局告警横幅与状态徽标；严重异常使用红色、明确图标和文字，不能只靠颜色传达。展示异常原因、影响范围、首次 / 最近发生时间、最近检查时间及建议处理方式，并可查看日志和手动重检。
- 后端持续检查，页面打开时立即获取最新状态，并通过轮询或事件更新；服务不可达时显示状态未知及最后更新时间，不能保留看似实时的绿色状态。
- 告警持久化并去重，重复检查更新同一事件；支持查看历史和标记已知晓，但“已知晓”不会清除故障或恢复绿色。只有后续检查确认恢复后才解除活动告警，并记录恢复时间。
- 阵列任务运行中按互斥策略等待或显示维护状态，避免重叠检查造成误报；任务卡住或超过维护时限仍需告警。应用重启后应恢复未解除告警和检查计划。
- 健康检查异常不自动触发 `fix`、删除或其他改写数据操作；缺盘、挂载异常及达到删除阈值时阻止自动 sync，要求先解决异常再重新检查。
- 首版要求应用内醒目告警；邮件、Webhook、推送等站外通知作为可选后续能力，渠道与接收人需另行配置。

数据范围与持久化：

- 照片、视频和 Live Photo 两个原始资源优先纳入保护；每个原始文件继续遵循全局 SHA256 去重策略。
- 分片、转码临时文件和可再生成的预览默认不纳入；已发布的加密归档包是否纳入需结合容量确认。
- SQLite 等持续变化的数据库先生成一致性备份，再保护备份文件；不将在线数据库文件直接视为已验证的可恢复备份。
- content 元数据需按官方配置要求跨独立磁盘保留副本，配置和恢复索引也需备份；加密密钥另外保管。
- 数据盘目录布局、应用跨盘放置规则、校验盘数量及容量需设计并验证；不能把当前单目录原片存储视为已经支持多盘分配。

前置调研与验收：

- [ ] 核实目标 Debian ARM64 上 SnapRAID 的可用版本、命令和配置格式。
- [ ] 确定磁盘数量、容量、文件系统、现有数据、挂载点与期望容错数量；依据官方要求规划校验盘与 content 副本。
- [ ] 在 PVE 中明确磁盘由宿主机、LXC 还是存储虚拟机管理；验证挂载、目录映射、UID/GID 与最小权限。SnapRAID 文件级操作与 NPU / VPU 设备直通分别评估。
- [ ] 评估专用存储服务执行 SnapRAID、应用仅提交固定操作的方案；不向网页开放任意 shell 命令、任意路径或宿主机管理权限。
- [ ] 决定采用官方 daemon 还是应用任务调度，避免两套独立计划互相冲突。
- [ ] 设计稳定同步视图、删除保护、资源限流及与视频转码 / 115 上传的 I/O 协调。
- [ ] 在临时测试盘验证新增、重复上传、同步期间上传、缺盘、异常删除、中断、重启与互斥行为。
- [ ] 验证检查失败、超时、缺盘、scrub 错误、检查过期、服务离线、告警确认、重启和恢复场景；验证前端横幅及时更新，未解除异常不显示正常。
- [ ] 使用可丢弃测试数据做恢复演练，验证恢复照片 / 视频的 SHA256 与原片一致；不得在真实照片盘上自动执行破坏性测试。

## 3. 部署与 NPU：待验证的技术方向

### 3.1 目标环境

- 硬件：铭凡 MS-R1，此芯 P1，ARM64。
- 系统：Debian；如使用 NPU，需要兼容的此芯内核、驱动和用户态运行时。
- 虚拟化：用户希望使用 PVE；具体版本、软件源和宿主机内核待验证。
- 容器与依赖必须具备 ARM64 支持。

### 3.2 人脸处理流水线

```text
照片上传 → SHA256 去重 → 保存原片 → 后台照片处理
                                      ├─ 缩略图 / 元数据
                                      ├─ 人脸检测 → 对齐 → 特征提取 → 人物聚类
                                      └─ 增量打包 → 加密 → 115 同步 → 恢复校验
```

拟由 NPU 承担人脸检测和特征提取；解码、对齐、聚类、SHA256、加密和上传由 CPU / 存储 / 网络完成。

- 候选为固定输入尺寸的 CNN 检测器与人脸特征网络，例如 SCRFD 类、MobileFaceNet 或 ResNet 类模型；尚未选定或验证。
- 模型需经过算子兼容检查、校准量化、离线编译和板端正确性验证。
- 不能因为 ONNX 模型可在 CPU 上运行，就认定它可直接在 NPU 上运行。
- 必须比较量化前后的人脸检测结果、特征相似度及人物聚类质量。
- CPU / NPU 特征向量是否兼容需验证；保存模型与预处理版本，升级时支持重建索引。
- 保留 CPU 推理路径；NPU 的性能收益、吞吐量和功耗均待实测。

### 3.3 PVE 容器部署与设备访问（开发前置调研）

**部署目标已确定为在 PVE 环境中以容器运行应用。** 具体采用 PVE LXC，还是在 Debian 虚拟机内运行 Docker / Compose，需先调研和实机验证；当前仓库尚未提供经过验证的容器镜像或设备映射配置。

| 候选部署方式 | 前置验证项 |
| --- | --- |
| PVE → Debian LXC → 应用服务 | 宿主内核驱动、设备节点映射、非特权容器 UID/GID 与 cgroup 权限、用户态运行时兼容性 |
| PVE → Debian 虚拟机 → Docker / Compose | ARM64 客体、设备能否先交给虚拟机、客体驱动，再验证 Docker 设备映射 |
| 应用容器 + 独立硬件推理 / 转码服务 | 内部接口、访问控制、延迟、服务恢复与独立升级；作为无法直接访问设备时的备选方案 |

LXC 设备映射与虚拟机硬件直通分别调研，不能把其中一种成功视为另一种可行；不默认将板载 NPU / VPU 当作可直接进行 PCIe 直通的设备。

前置调研清单：

- [ ] **宿主环境**：记录 MS-R1 BIOS、PVE 来源及版本、Debian 与内核版本；验证所用内核能否同时满足 PVE 和此芯设备驱动要求。
- [ ] **设备盘点**：确认实际 NPU、VPU、GPU 的总线类型、驱动、设备节点与权限，不预先写死设备路径。
- [ ] **NPU**：裸机跑通参考模型，再验证容器中的 KMD / UMD / SDK 配套、设备访问、人脸模型正确性与性能。
- [ ] **VPU / FFmpeg**：分别验证 ARM64 软件转码和此芯硬件编解码；检查 FFmpeg 后端、驱动、设备权限及真实大视频，不以“列出编码器”作为加速成功依据。
- [ ] **GPU（按需）**：仅在选定方案实际需要时验证设备映射、用户态库及预览 / 推理兼容性。
- [ ] **LXC 权限**：优先验证非特权容器及最小设备授权；如需额外权限，记录具体原因和影响，不以全局特权模式作为默认方案。
- [ ] **VM 直通（仅 VM 路线需要）**：验证 IOMMU / SMMU、设备隔离与绑定、客体驱动及设备复位能力；无法满足时记录限制并评估独立硬件服务。
- [ ] **容器封装**：ARM64 镜像构建、依赖版本锁定、运行用户、设备参数与软件推理 / 转码降级配置。
- [ ] **持久化与大文件**：原片、SQLite、分片、预览、密钥分别规划持久化位置与权限；验证 10 GiB 上传、空间不足及容器重建后的数据保留。
- [ ] **运维与恢复**：容器 / PVE 重启后的设备可用性、分片续传、任务恢复、升级回滚；明确 PVE 备份是否覆盖外部挂载的数据。

调研交付物应包括：可行部署拓扑、版本与设备清单、最小复现命令、容器配置示例、性能结果、限制和降级方案。先完成裸机基线，再在最终容器部署环境复测；未取得实机证据前，不承诺 NPU / VPU 直通或硬件加速可用。

拟将人脸推理和视频转码保持为独立服务边界，避免具体设备部署方式影响照片上传、去重与备份逻辑。

## 4. 实现路线尚未确定

优先评估以下方案，而非现在锁定技术栈：

| 路线 | 需验证的问题 |
| --- | --- |
| 复用 Immich / PhotoPrism，加独立归档服务 | ARM64 支持、接口能力、原片去重语义、人脸推理后端替换方式 |
| 自建轻量照片管理服务 | 首版范围、上传体验、人物相册与长期维护成本 |

115 接入需验证可用接口、账号授权、上传限制、失败恢复及远端校验能力，不预先承诺某个客户端或库可用。

## 5. 分阶段计划

1. **需求确认**：明确首版范围、数据规模、用户模式和备份策略。
2. **技术验证**：优先完成第 3.3 节的 PVE 容器部署与设备访问调研，并对 NPU 人脸模型、FFmpeg / VPU、SnapRAID 测试阵列与恢复演练、115 加密包上传与恢复分别做最小验证。
3. **最小可用版本**：照片上传、SHA256 去重、后台任务、增量加密备份与状态查看。
4. **人物相册**：接入经过验证的人脸流水线与人工纠正功能。
5. **稳定性完善**：故障恢复、任务重试、索引重建及部署文档。

若 NPU 验证不通过，需明确报告限制，再决定 CPU 方案与首版性能目标。

## 6. 首版拟议验收标准

- 同一文件连续上传或并发上传，最终均只保留一份原片。
- 重复上传不会重复进入后续归档包。
- 上传成功后的照片可浏览，后台任务状态可查询，失败可重试。
- 云端归档包及恢复清单均受加密保护，无法直接读取原始照片和文件名。
- 上传中断后重试不会产生重复归档记录或错误的成功状态。
- 从 115 下载归档，在独立恢复环境中解密，恢复照片的 SHA256 与原始值一致。
- 人脸识别能对测试照片分组，并允许纠正误分；识别准确率和速度目标在样本测试后确定。
- 若启用 NPU，提供与 CPU 的准确率和端到端性能对照，证明主推理实际运行在 NPU。
